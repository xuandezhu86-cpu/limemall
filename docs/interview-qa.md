# 面试追问清单（LimeMall 项目）

> 用法：先自己讲一遍项目，再对着下面每一条自问自答。
> **标 ⚠️ 的是"必须能答"的高频题**；标 🔍 的是面试官很可能继续追问的方向。
> 所有数据都来自本项目真实压测，回答时直接报数字，比说"性能提升明显"可信得多。

---

## 一、项目整体

**Q1：介绍一下这个项目。**
> 青柠商城是一套 Spring Cloud Alibaba 的电商微服务系统，我做了商品、购物车、用户、交易、支付五个服务，另外**自己新增了一个秒杀服务**和**商品详情的多级缓存**。
> 技术栈是 Spring Boot 2.7 + Spring Cloud Alibaba（Nacos/Sentinel/Seata）+ MySQL + Redis + RabbitMQ，部署用 Docker Compose 一键起 10 个容器。
> 我做的最主要的三件事：一是秒杀链路，用 Redis+Lua 原子预扣 + 令牌桶限流 + MQ 异步削峰，200 用户抢 100 件实测零超卖；二是商品详情的 Caffeine+Redis 两级缓存，把商品详情接口从 2,689 TPS 提到 13,383 TPS；三是可观测性，接了 Prometheus+Grafana+7 条告警和 Sleuth+Zipkin 链路追踪，并用 JMeter 做了完整压测。

**Q2：为什么用微服务？单体不行吗？** 🔍
> 项目里其实两套都有：`lm-shop` 是单体版本，`lm-*` 是拆开后的微服务版本。拆分的直接收益是**按业务独立扩容和独立故障隔离**——比如秒杀流量只会打到 seckill-service，不会把商品、订单一起拖垮。
> 代价也很明确：分布式事务、链路追踪、配置管理这些复杂度都上来了。所以如果业务量不大、团队小，我会倾向单体+模块化，而不是一上来就微服务。

**Q3：服务之间怎么调用？** 🔍
> 内部用 OpenFeign（`lm-api` 模块统一定义 Feign 接口和 DTO，避免各服务重复声明），开启了 OkHttp 连接池；外部流量统一走 Spring Cloud Gateway。
> 网关做两件事：路由转发和 JWT 鉴权，校验通过后把 userId 放进 `user-info` 请求头传给下游，业务服务通过拦截器塞进 ThreadLocal（`UserContext`），所以业务代码里随时能拿到当前用户。

**Q4：配置怎么管理？**
> 放 Nacos 配置中心，每个服务一个 `bootstrap.yaml` 声明自己的 dataId，公共部分抽成 `shared-jdbc`、`shared-log`、`shared-swagger`、`shared-seata` 四个共享配置，改数据库连接、日志级别不用动代码。
> 本地敏感配置（数据库密码）走 profile 隔离，`application-dev.yaml` 里放本地值。

## 二、秒杀专题（重头戏）

**Q5：⚠️ 怎么防止超卖？**
> 核心是**把"判断"和"扣减"做成一个原子操作**。我用 Redis + Lua 脚本，脚本里一次做完四件事：读库存、判断是否售罄、判断这个用户是否已经买过（`SISMEMBER`）、`DECR` 库存并 `SADD` 记录买家。
> Redis 执行 Lua 是单线程的，所以这四步之间不会插入其他请求，天然没有"先查后改"的并发窗口。
> 数据库层还有第二道防线：扣库存用 `UPDATE item SET stock = stock - #{num} WHERE id = ? AND stock >= #{num}`，靠 `stock >= num` 条件和行锁兜底；秒杀订单表建了 `uk_activity_user` 唯一索引，重复下单会直接插入失败。

**Q6：⚠️ 为什么用 Lua，不用 Redis 的 DECR？**
> 只用 `DECR` 的话，库存判断和去重还得在 Java 里做，就变成了"先查后改"：两个请求可能都查到库存为 1，然后都去扣，就超卖了（或者用户重复下单）。
> Lua 把多步合成一步，省掉的正是这个窗口。另外也省了多次网络往返。

**Q7：⚠️ 为什么要用 MQ？直接写库不行吗？** 🔍
> 直接写库有两个问题：一是**数据库连接和行锁会成为瓶颈**——我压测里做了对照实现 `POST /seckill/legacy/{id}`，用 `SELECT ... FOR UPDATE` 悲观锁 + 同步落库，200 用户抢 100 件只有 43.5 TPS、平均 3,472ms；换成 Redis 预扣 + MQ 异步后是 105 TPS、平均 1,442ms，快 2.4 倍。
> 二是**削峰**：突发流量进到 MQ 里排队，数据库按自己的节奏消费，不会被瞬时并发打挂。

**Q8：🔍 那 2.4 倍是不是不够多？瓶颈在哪？**
> 因为这是**一次性 200 并发**，瓶颈其实在网关的 JWT 校验和限流器上，Redis 本身远没到瓶颈。legacy 那边事务也很短（本地库 + 一次 Feign 调用），所以差距没有拉得很夸张。
> 如果库存和并发放大到几千，legacy 的行锁等待会线性恶化，而异步方案基本恒定——想看这个效果把 `-Jthreads` 提到 1000 再跑一次就知道了。

**Q9：⚠️ MQ 消费失败了怎么办？消息丢了怎么办？**
> 分几层：
> ① 生产端投递失败会**立刻回补 Redis 预扣**（`rollbackRedis`），不会把库存白扣；
> ② 消费端用本地事务落库，`@RabbitListener` 打开手动重试（3 次，指数退避），失败进死信；
> ③ 最后有**定时对账任务**（每 30 秒）扫描状态是"处理中"且超过 30 秒的订单，做补偿或回补库存，同时比对 Redis 与 DB 的库存差异，超过容忍度就告警。
> 这就是最终一致性：不追求任何时刻强一致，但保证最终会一致，且异常能被发现。

**Q10：⚠️ 一人一单怎么做的？**
> Redis 侧用 Set 记录已下单用户（`SISMEMBER` 判断），挡掉绝大多数重复请求；数据库侧 `seckill_order` 上有 `uk_activity_user(activity_id, user_id)` 唯一索引，万一 Redis 数据丢了或并发穿透，插入会失败，消费端捕获后回补库存。
> 为什么不只用数据库唯一索引？因为那意味着重复请求都要打到数据库，Redis 这层是为了在入口就挡掉。

**Q11：令牌桶限流是怎么实现的？** 🔍
> 用 Redis + Lua 实现：key 里存"当前令牌数 + 上次补充时间"，请求进来先按流逝时间补充令牌（`min(容量, 当前 + 速率×时长)`），够 1 个就扣掉放行，不够就拒绝。
> 配置是容量 3000、速率 1500/s（按活动维度）。用它而不是计数器，是因为令牌桶允许**突发流量**——秒杀开场那一瞬间本来就是突发的，固定窗口计数器会把正常用户也拦掉。

**Q12：🔍 用户在页面狂点怎么办？ / 前端有没有做限制？**
> 后端这一层：Redis 的一人一单会直接拒绝第二次；限流器也会兜。前端可以做按钮置灰 + 倒计时，但那只是体验优化，不能作为防护手段——**真正的防护必须在服务端**。

**Q13：🔍 秒杀的活动信息怎么读？**
> 活动信息（价格、时间窗、库存）走 Redis 缓存，未命中回源 DB 并预热；提供 `POST /seckill/activity/{id}/warmup` 在活动上线前主动预热，避免开场瞬间大量请求同时回源。
> 如果缓存不存在（没预热），Lua 返回 -2，本次请求按失败处理并主动预热，让用户重试——宁可失败一次，也不让流量直接打到数据库。

**Q13.1：⚠️ 抢到的商品会进购物车吗？订单怎么支付？**
> **不会进购物车，这是有意的**：秒杀是「直接成单」，不走购物车——真实电商也是这个逻辑，否则用户还要多一步加购结算，而且购物车的价格是按商品当前价算的，跟秒杀价对不上。
> 但订单必须能支付，这是完整闭环的关键：秒杀服务在预扣时就生成雪花订单号，异步落库后带着这个订单号调交易服务的**内部接口**建一笔交易订单（价格用秒杀价、不再扣库存、不动购物车），两边**复用同一个订单号**，所以用户凭页面上的订单号就能走正常支付流程，不需要额外的映射表。
>
> 这里有两个细节值得说：
> ① 内部接口放在 `/internal/**` 前缀下，网关只路由 `/seckill`、`/orders` 这些业务前缀，所以**外部访问不到**（实测经网关返回 404）；
> ② 支付成功后 `pay.direct` 交换机会广播支付成功消息，交易服务和秒杀服务各绑一个队列同时消费，分别把自己的订单状态改成「已支付」。

**Q13.2：🔍 补偿重试会不会把库存扣两次？**
> 会——如果不对状态做区分的话。比如「扣完活动库存、扣商品库存时报错」，MQ 重试或定时对账再进来就会重复扣减。
> 我的处理是在订单上加一个**中间状态** `STATUS_STOCK_DEDUCTED`：库存扣减完成后先把状态推进到这里，重试进来发现已是这个状态就跳过扣减、只补做后面的建单动作。对账任务扫描的也是「处理中 + 库存已扣未建单」这两种状态。

## 三、缓存专题

**Q14：⚠️ 缓存穿透、击穿、雪崩分别是什么？你怎么解决的？**
> **穿透**：查一个数据库里根本不存在的 id，缓存永远不命中，每次都打库。我用**布隆过滤器**（Redis 位图，16M bit、4 个 MD5 哈希）在入口拦截；布隆有误判率，万一说"可能存在"但库里没有，就用**空值缓存**兜底（60 秒）。
> **击穿**：热点 key 过期瞬间大量请求同时回源。我用 **Redis SETNX 互斥锁**，只放一个线程去查库重建，其他线程以 50ms 间隔自旋等待（最多 5 次）；极端情况自旋超时就退化为直接查库，保证请求不会被无限阻塞。
> **雪崩**：大批 key 同时失效。我给 L2 过期时间加了 **0~60 秒随机抖动**，并且 L1 是 30 秒短 TTL，能吸收掉大部分热点读。

**Q15：⚠️ 为什么要做两级缓存？只用 Redis 不行吗？** 🔍
> 一级用 Caffeine 是因为它是**进程内缓存**，命中时是纳秒级，连网络往返都省了；二级 Redis 做共享层，保证多实例之间数据一致。
> 只用 Redis 也能用，但热点商品的 QPS 会全部压到 Redis 上。实测 40 万次请求里 L1 命中 400,046 次、只回源数据库 3 次，L1 把绝大部分流量都挡在了本地。

**Q16：⚠️ 两级缓存怎么保证一致性？多实例的本地缓存怎么办？** 🔍🔍
> 写路径用 **Cache Aside**：先更新数据库，再删 L2，最后通过 RabbitMQ 的 **fanout 交换机广播**一条失效消息。
> 每个服务实例启动时绑定一个**匿名队列**（exclusive + auto-delete），所以每条广播消息**所有实例都能收到**，各自清掉自己进程里的 L1。这样一个实例改了商品，另一个实例的本地缓存也会立刻失效。
> 实测：实例 B 把价格从 990 改成 991，实例 A 立刻就能读到 991（`infra/tools/cache-bench.ps1` 会验证这一步）。

**Q17：🔍 为什么是删除缓存而不是更新缓存？**
> 更新缓存有两个问题：一是并发更新时，两个请求的写入顺序可能和数据库提交顺序不一致，缓存里留下旧值；二是如果这个缓存值很复杂（要聚合多张表），每次更新都重算很浪费，而删掉是**懒加载**，下次真有人读再算。
> "先删缓存再更新库"也不行，会出现"删了缓存→读请求回源读到旧值写回缓存→库才更新完"的经典时序问题，所以标准做法是**先更新数据库，再删缓存**。

**Q18：🔍 那"先更新库再删缓存"就绝对没问题吗？**
> 极端情况下仍有短暂不一致：读请求在"删缓存"之前拿到旧值，但写回缓存的时机在删除之后。所以我的兜底是**短 TTL**（L1 30 秒、L2 10 分钟 + 抖动），不一致窗口最多一个有界时间。
> 如果需要更强保证，可以上**延迟双删**或者订阅 binlog（Canal）异步失效——但那是用复杂度换一致性，本项目场景短 TTL 足够。

**Q19：布隆过滤器为什么能防穿透？它的缺点是什么？** 🔍
> 它把元素映射到位图的 k 个 bit 上，判断时只要有一个 bit 是 0，就说明元素**一定不存在**——所以能拦掉所有不存在的 id（代价是有误判：说存在但实际不存在）。
> 缺点有三个：① 有误判率（我用 16M bit / 4 个哈希，容量和误判率做了权衡）；② **标准布隆不能删除元素**，所以商品下架后我不用它做删除，而是靠空值缓存兜底；③ 数据量大到超过设计容量时误判率会飙升，需要重建（我留了 `POST /items/cache/bloom/rebuild` 接口）。

**Q20：🔍 缓存和数据库的双写，你压测过一致性吗？**
> 压测脚本里专门有一段：先从实例 A 读（把值灌进 A 的 L1 和 L2），再从实例 B 更新价格，然后立刻回实例 A 读——如果 A 还能读到旧值就说明广播失效没生效。实测是马上读到新值。
> 另外还有一段验证缓存击穿：先把 key 失效，然后 60 个并发打过来，看服务端"回源数据库次数"这个指标只涨了 1 —— 证明互斥锁真的只放了一个线程进去。

## 四、分布式事务与一致性

**Q21：⚠️ 下单要跨库存、购物车、订单三个库，怎么保证一致性？**
> 用 Seata AT 模式，下单方法上加 `@GlobalTransactional`。库存扣减和购物车清理是 Feign 调用的分支事务，每个分支都写自己的 `undo_log`；订单落库是本地事务。任一分支失败，协调器根据 undo_log 做反向补偿回滚。
> 选 AT 是因为对业务代码几乎无侵入——不用像 TCC 那样为每个参与方写 try/confirm/cancel 三套接口。

**Q22：🔍 AT 模式的原理是什么？**
> 两个阶段：一阶段执行业务 SQL 并把**前置镜像（before image）和后置镜像（after image）**记到 `undo_log`，同时申请全局锁；二阶段如果全局提交就异步删 undo_log，如果回滚就用 before image 生成反向 SQL 补偿，并校验 after image 确认数据没被别的事务改过（防脏写）。

**Q23：🔍 Seata 有什么坑？**
> 踩过一个：Seata Server 跑在容器里，注册到 Nacos 的是容器内网 IP（172.x），宿主机根本路由不到，客户端一直报 `no available service 'default' found`。改成客户端用 file 注册 + `grouplist: 127.0.0.1:8091` 直连映射端口就好了。
> 另外每个用 Seata 的库都必须有 `undo_log` 表，不然一阶段直接失败。

**Q24：⚠️ 为什么秒杀不用 Seata？**
> 因为目标不同。秒杀追求**高吞吐**，而全局事务会加全局锁、增加 RTT，200 并发下就是灾难。秒杀我用的是**最终一致**：Redis 预扣保证不超卖，MQ 保证请求不丢，对账任务保证最终数据正确。
> 一句话总结我的取舍标准：**强一致场景（下单）用 Seata，高并发场景（秒杀）用最终一致性 + 补偿**。

**Q25：🔍 支付成功后怎么通知交易服务改订单状态？**
> 走 RabbitMQ。pay-service 扣完余额、更新支付单后发消息，trade-service 消费后把订单改成"已付款"。这里用消息而不是 Feign 同步调用，是为了让支付不被交易服务拖住；消息失败有重试和订单状态兜底（交易服务可以主动查支付单）。

## 五、可观测性与压测

**Q26：⚠️ 你怎么知道系统跑得好不好？**
> 三层：
> ① **指标**：每个服务接 Actuator + Micrometer，暴露 `/actuator/prometheus`，Prometheus 每 5 秒抓一次，Grafana 上做了 12 个面板（QPS、P95、5xx、JVM 堆、HikariCP 连接、MQ 收发，还有我自己埋的缓存命中/回源指标）。
> ② **告警**：7 条规则，比如服务掉线 30 秒、5xx 速率超阈值、P95 超过 500ms、堆使用率超 85%、连接池超 80%、缓存命中率低于 50%、缓存回源过高。
> ③ **链路**：Sleuth + Zipkin，一次下单能看到 20 多个 span 的跨服务调用树，还能看到 Redis 命令和 MQ 的生产消费。

**Q27：🔍 自定义指标怎么埋的？**
> 注入 Micrometer 的 `MeterRegistry`，用 `Gauge.builder` 把缓存里的计数器（L1 命中、L2 命中、回源次数、布隆拦截、锁重建次数）注册成指标，名字统一 `limemall_cache_` 前缀。这样 Grafana 上能直接看"缓存命中 vs 回源"的曲线，压测时一眼就能看出缓存有没有生效。

**Q28：⚠️ 压测怎么做的？**
> JMeter 5.6.3 非 GUI 模式，写了两个参数化脚本：`item-detail.jmx` 用 `-Jpath` 切换"走缓存 / 直连 DB"，`seckill.jmx` 用 CSV 给每个线程一个独立用户的 JWT。
> 结果：商品详情 50 并发 30 秒，走缓存 13,383 TPS / 平均 3.4ms，直连 DB 2,689 TPS / 17.1ms；秒杀 200 用户抢 100 件，优化版 105 TPS / 1,442ms，legacy 版 43.5 TPS / 3,472ms，两版都没超卖。
> 原始结果和报告都在仓库里（`infra/jmeter/`、`docs/load-test-report.md`）。

**Q29：🔍 压测中发现了什么问题？**
> 三个真实问题：① 一开始直接压秒杀服务（8087）全部返回 500，日志是 `UnauthorizedException` —— 因为业务服务依赖网关注入的用户身份，绕过网关根本没有身份，后来改成经网关压测（这也更接近真实流量）；② 监控面板的 P95 一直是空的，查下来是 Spring Boot 默认**不导出 HTTP 延迟直方图**，打开 `percentiles-histogram` 才有；③ 机器上 8 个 JVM 各占约 900MB，可用内存只剩 2.8G，服务被 GC 拖到接口超时，后来给启动脚本加了堆上限。

**Q30：🔍 如果压测发现 TPS 上不去，你会怎么排查？**
> 按"从外到内"的顺序：先看客户端是不是瓶颈（JMeter 和被测服务在同一台机器上会互相抢资源）；再看网关层（连接数、JWT 校验开销）；然后看服务自身（线程池排队、GC、日志级别——我的服务开着 MyBatis DEBUG 日志，压测时 I/O 很可观）；最后看下游（数据库慢 SQL、连接池、Redis 延迟、MQ 堆积）。
> 我这次的抓手就是 Grafana 面板 + 链路追踪，能看到耗时到底花在哪个 span 上。

## 六、收尾类问题

**Q31：这个项目里你遇到的最难的问题是什么？**
> 选一个真实的讲，比如"多实例本地缓存不一致"：一开始只有 Redis 缓存，加了 Caffeine 之后发现 A 实例修改商品，B 实例因为本地缓存还在，继续返回旧价格。解决办法是广播失效——用 fanout 交换机 + 每个实例一个匿名队列，保证每条失效消息所有实例都能收到。这个过程中还踩到"匿名队列名要在 `@RabbitListener` 里用 SpEL 引用"这类细节。

**Q32：如果让你继续优化，你会做什么？**
> 三件事：① 秒杀压到 1000 并发、库存 1000 再看两个方案的真实差距，把"线性恶化"验证出来；② 缓存一致性上 Canal 订阅 binlog 做异步失效，把不一致窗口从"TTL 级"缩到"毫秒级"；③ 部署上把单机 Compose 换成 K8s，服务做真正的弹性扩缩容，现在还是单点。

**Q33：⚠️ 这个项目是你自己写的吗？哪部分参考了别人的？**
> 诚实的回答方式：**课程项目做过基础版**（微服务拆分、下单支付链路），**秒杀服务、多级缓存、可观测性、压测这四块是我自己加的**，代码、脚本、压测数据都在仓库里，可以随时讲实现细节。
> 面试官最想确认的是"你是不是真的懂"，所以**别否认参考，也别夸大**，把你能讲清楚的部分讲透。

**Q34：🔍 有什么是你没做过、不确定的？**
> 直接说不确定比硬编好。可以说：生产级的容量规划、多机房容灾、K8s 运维这些我只有在课程和文档里了解，没有真实环境经验；这个项目的量级也远没到需要分库分表。**承认边界反而加分**，因为面试官一眼能看出硬编的答案。
